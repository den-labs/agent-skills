## P0 — Bloqueantes (romper instalación / pérdida de fondos)

### 1. `skills/alchemy-contribute` quedó convertido en symlink roto para git
`npx skills add` reemplazó el directorio real por un symlink a `../.agents/skills/alchemy-contribute`. Git ve los 3 archivos originales como **borrados**:

```
D skills/alchemy-contribute/SKILL.md
D skills/alchemy-contribute/references/alchemy-context.md
D skills/alchemy-contribute/references/pr-template.md
```

Si se commitea así, el skill desaparece del repo publicado y `npx skills add den-labs/agent-skills` deja de resolverlo.

**Acción:** restaurar los archivos reales (`git checkout -- skills/alchemy-contribute` tras borrar el symlink), y añadir `.gitignore` con `.agents/` y `skills-lock.json` (son artefactos de *consumo* de skills, no del repo fuente).

### 2. `register.sh` usa **mainnet por defecto** y gasta gas sin confirmación
`NETWORK="${NETWORK:-mainnet}"` en ambos skills. Un usuario que copie el ejemplo del README manda una tx real en Celo/Avalanche mainnet sin ningún gate. Contradice la propia política de "confirmación solo en pasos irreversibles" que predica `alchemy-contribute`.

**Acción:** default a testnet, o exigir `--yes` / prompt explícito cuando `NETWORK=mainnet`.

### 3. Éxito reportado sin verificar el receipt
- `register.sh`: `sleep 3` fijo y luego `cast receipt`; si el bloque tarda más, cae al mensaje ambiguo. Nunca comprueba `status == 1`, así que una tx **revertida** se reporta igual.
- `give-feedback.sh`: imprime `"Feedback submitted successfully!"` inmediatamente tras `cast send`, sin esperar receipt en absoluto.

**Acción:** usar `cast send --confirmations 1` y validar `.status` del receipt antes de declarar éxito.

### 4. `PRIVATE_KEY` en variable de entorno como único método
Ambos skills exigen la clave privada en plano en el entorno del agente. `cast` soporta `--account <keystore>`, `--ledger`, `--trezor`, `--interactive`.

**Acción:** soportar keystore/hardware wallet y degradar `PRIVATE_KEY` a fallback documentado con advertencia.

## P1 — Robustez

### 5. Parsing de JSON con `grep -o` / `cut`
Cinco ocurrencias (`register.sh` x2, `give-feedback.sh`, respuesta de Pinata). Frágil ante cambios de formato o espacios.
**Acción:** usar `jq` con check de disponibilidad al inicio, igual que ya se hace con `cast`.

### 6. `get-score.sh` depende de `python3` sin verificarlo
El bloque de parseo termina en `|| echo "$BODY"`, así que un fallo real de datos se enmascara como "no hay python".
**Acción:** `jq` en vez de python3, y verificar dependencias explícitamente.

### 7. `mktemp /tmp/...` ignora `TMPDIR`
En `register.sh`. Además el `trap` de limpieza no existe: si `curl` falla, el temporal con el JSON queda huérfano.
**Acción:** `mktemp -t` + `trap 'rm -f "$TMPFILE"' EXIT`.

### 8. Cero validación automatizada
No hay shellcheck, ni validador de frontmatter (`name`/`description` presentes, `name` == nombre del directorio), ni chequeo de que cada `SKILL.md` referenciado exista.

## P2 — Duplicación y mantenibilidad

### 9. `erc8004-avalanche` y `erc8004-celo` son ~95% el mismo contenido
Mismos 177 renglones de SKILL.md, mismas 3 references, mismos 3 scripts — sólo cambian RPC, chain ID, explorer y símbolo del token. Las direcciones de los registries son **idénticas en ambas cadenas** (deploys deterministas `0x8004...`).

Cada cambio hay que aplicarlo dos veces, y ya hay evidencia de deriva (el `README` menciona Celo Sepolia pero `contract-addresses.md` de Avalanche todavía lista Celo en una nota cruzada).

**Opciones:**
- **A (recomendada):** un único skill `erc8004` multi-chain con tabla de redes, y scripts que resuelvan la red por `NETWORK=celo|celo-sepolia|avalanche|fuji`. Los skills por cadena quedan como alias delgados si se quiere preservar el descubrimiento por nombre.
- **B:** mantener dos skills pero generar `references/` y `scripts/` desde una plantilla + `networks.json`, con un test que falle si divergen.

### 10. README desincronizado
- No lista `trust-score` en la tabla de skills (existe en el repo desde `fbf6750`).
- Duplica las tablas de direcciones que ya viven en `references/contract-addresses.md` — tercera copia de la misma verdad.
